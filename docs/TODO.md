# rewater-agent 迁移路线

## 使用说明

- 本文中的“修改文件”表示预计影响范围，不代表当前任务已经修改这些业务文件。
- 新文件或最终命名可以在实施方案评审时调整。
- P0 为阻断迁移或运行的问题，P1 为核心能力，P2 为增强项。
- 每次实施只解决一个可验证问题，并补充测试。
- 路线聚焦高质量 AI Agent 应用工程，不以建设完整企业 SaaS 为目标。

## 阶段 1：清理商品识别业务代码

### 1.1 建立迁移基线和契约测试

- 目标：固定导入图、查询图和 state 的真实输入输出，避免迁移时继续扩大接口漂移。
- 修改文件：`app/process/*/agent/state.py`、查询节点、查询 service；新增 `tests/unit/` 和 `tests/contract/`。
- 优先级：P0。
- 预期效果：查询包可导入，各节点返回值类型明确，外部服务可用 mock 替代。

### 1.2 修复当前查询链路接口漂移

- 目标：统一不存在的函数名、Milvus 集合属性和 node/service 返回契约。
- 修改文件：`app/rag/query/__init__.py`、`app/process/query/agent/nodes/`、`app/rag/query/*_service.py`。
- 优先级：P0。
- 预期效果：当前基线链路至少可以在 mock 环境完成端到端执行，为后续替换提供安全网。

### 1.3 定义行业查询与导入状态模型

- 目标：用 `document metadata`、`retrieval_plan`、`evidence` 等字段替代商品 `item_names` 核心状态。
- 修改文件：`app/process/import_/agent/state.py`、`app/process/query/agent/state.py`；可能新增 `app/api/schemas/metadata.py`。
- 优先级：P0。
- 预期效果：状态模型表达再生水行业需求，不再要求商品主体。

### 1.4 替换商品主体识别流程

- 目标：将导入主体识别替换为文种、地域、主题、时效和来源 metadata 抽取；将查询主体确认替换为意图识别与 Query Rewrite。
- 修改文件：`app/rag/import_/item_name_service.py`、`app/rag/query/item_name_confirm_service.py`、对应节点、Prompt。建议先新增新服务再切换图，最终名称待方案确认。
- 优先级：P0。
- 预期效果：商品名称不再是导入和查询的前置条件。

### 1.5 迁移并最终删除商品资产

- 目标：在新链路和测试稳定后，删除商品 Prompt、HAK180 数据、`item_name_collection` 依赖和商品阈值逻辑。
- 修改文件：`app/resources/prompts/`、`app/rag_eval/artifacts/`、Milvus 配置和旧 service。
- 优先级：P1。
- 预期效果：仓库中不再残留会误导后续开发的商品业务语义。
- 前置条件：行业链路、数据迁移和回归测试均通过；执行前必须单独提出删除清单。

## 阶段 2：建设再生水知识库 RAG

### 2.1 建立行业分类与 metadata Schema

- 目标：落地文种、地域、主题、效力和来源等核心字段及枚举。
- 修改文件：建议新增 `app/domain/knowledge/` 或等价领域模块；调整 API schemas、导入 state 和配置。
- 优先级：P0。
- 预期效果：所有知识文件使用统一、可校验、可扩展的 metadata。

### 2.2 建设 metadata 抽取与质量验证

- 目标：结合规则和 LLM 抽取 metadata，通过样本、日志和评测验证抽取质量。
- 修改文件：导入图、新的 metadata service、Prompt 和测试数据。
- 优先级：P1。
- 预期效果：地域、文种和主题字段可稳定支撑检索过滤。

### 2.3 重构结构感知 Chunk

- 目标：支持法规条款、标准章节、规划指标、论文结构和表格切分，保留页码与章节路径。
- 修改文件：`app/rag/import_/split_service.py`、解析结果模型、切分测试。
- 优先级：P1。
- 预期效果：chunk 语义完整且可准确引用原文。

### 2.4 设计并迁移 Milvus Schema

- 目标：用文档 ID 和行业 metadata 代替商品过滤，统一 Dense/Sparse metric。
- 修改文件：`app/rag/import_/index_service.py`、`app/infra/vector_store/`、Milvus 配置、迁移脚本。
- 优先级：P0。
- 预期效果：支持地域、文种、主题和时效的混合过滤；旧数据可控迁移。

### 2.5 建设可靠导入流程

- 目标：增加内容 hash、失败重试、导入状态和可靠索引写入。
- 修改文件：导入图、PDF/图片/Embedding/索引 service、任务仓储。
- 优先级：P1。
- 预期效果：部分 Embedding 失败不会被误报成功，失败导入不会留下不完整索引。

### 2.6 重构 Query Rewrite 和多路检索

- 目标：输出结构化检索计划，执行 Dense、Sparse、metadata 和精确编号检索。
- 修改文件：查询入口 service、Prompt、`search_embedding_service.py`、Milvus gateway。
- 优先级：P0。
- 预期效果：问题可按地域、文种、主题、有效性和时间范围检索。

### 2.7 修复融合、降级和 Rerank

- 目标：统一多路候选格式，支持单路失败降级，并通过行业评测集校准 RRF、Rerank 和 Top-K。
- 修改文件：`rrf_service.py`、`rerank_service.py`、相关节点和评测模块。
- 优先级：P1。
- 预期效果：网络或 HyDE 失败不阻断本地 RAG，最终证据相关且具有多样性。

### 2.8 建设引用与证据回答

- 目标：输出文档标题、条款、页码、版本和来源，区分规定、研究结论与模型建议。
- 修改文件：`answer_output_service.py`、答案 Prompt、API response schema、前端页面。
- 优先级：P1。
- 预期效果：行业用户可以核对每项关键结论。

### 2.9 建立行业 RAG 评测集

- 目标：替换商品样本，覆盖国家、广东、深圳、区级及六类以上专业主题。
- 修改文件：`app/rag_eval/`、`tests/`、评测 artifacts。
- 优先级：P1。
- 预期效果：所有检索和 Prompt 调整都有可量化回归依据。

## 阶段 3：增加 Agent 能力

### 3.1 建立意图路由与澄清机制

- 目标：区分事实查询、标准查找、地区对比、文件摘要、技术对比和证据不足场景。
- 修改文件：查询 LangGraph、state、路由节点和 Prompt。
- 优先级：P1。
- 预期效果：不同问题使用合适流程，条件不明确时主动澄清。

### 3.2 建立行业工具注册机制

- 目标：复用现有工具调用基础，接入经过批准的标准查询、单位换算、指标核查等工具。
- 修改文件：建议新增轻量工具注册模块，调整 Agent 图。
- 优先级：P1。
- 预期效果：Agent 能执行可验证操作，而不只生成文本。
- 待确认：首批工具、数据源授权和计算责任边界。

### 3.3 增加多文档对比与冲突识别

- 目标：比较地区政策、标准版本和技术路线，显式展示差异和适用条件。
- 修改文件：检索规划、证据组织、回答 service 和 UI。
- 优先级：P1。
- 预期效果：支持规划设计和政策研究中的高价值对比场景。

## 阶段 4：工程化和部署

### 4.1 输入安全与健壮性

- 目标：增加上传限制、路径净化、Zip Slip 防护、外部内容隔离和 Prompt Injection 防护。
- 修改文件：API、PDF/图片 service、对象存储、配置和安全测试。
- 优先级：P0（生产前）。
- 预期效果：文件和联网内容不会破坏应用或污染 Agent 指令。

### 4.2 任务与 SSE 生命周期治理

- 目标：为进程内任务和 SSE 队列增加超时、清理、失败状态与断连处理。
- 修改文件：`task_utils.py`、`sse_utils.py`、API 和任务执行层。
- 优先级：P1。
- 预期效果：当前单实例 Agent 演示长期运行时不会持续泄漏状态。

### 4.3 模型推理和性能治理

- 目标：管理 Embedding/Rerank 模型服务、批处理、并发、缓存、超时和熔断。
- 修改文件：LLM provider、模型工具、检索链路和部署配置。
- 优先级：P1。
- 预期效果：满足目标并发和响应时间，避免模型重复加载。

### 4.4 可观测性与质量门禁

- 目标：利用现有日志记录 trace、节点延迟、模型调用和错误，并建立测试与 CI 门禁。
- 修改文件：日志、LangGraph 装饰器、RAG Eval、测试和 CI 配置。
- 优先级：P1。
- 预期效果：Agent Workflow 可调试，发布前自动执行质量回归。

### 4.5 容器化、配置与部署文档

- 目标：统一依赖来源、环境变量、健康检查、数据备份和部署步骤。
- 修改文件：`pyproject.toml`、容器/编排配置、README 和运维文档。
- 优先级：P1。
- 预期效果：开发、测试和生产环境可重复部署。

## 推荐执行顺序

1. 先做 1.1、1.2，得到可以测试的稳定技术基线。
2. 完成 1.3 和 2.1，确定行业状态模型与 metadata 契约。
3. 实施 1.4，同时完成 2.3、2.4、2.6 的最小闭环。
4. 用 2.9 行业评测集校准检索、融合、Rerank 和回答。
5. 完成 2.5、2.8 后，再执行 1.5 的旧商品资产删除。
6. 在知识链路稳定后扩展阶段 3 Agent 工具。
7. 生产发布前完成阶段 4，安全加固应提前穿插执行。
