# tests 代码解读与项目评估改进指南

> 面向对象：第一次接触 Agent、RAG 测试与评估的开发者  
> 分析范围：`tests/`、`app/rag_eval/`、相关导入/查询流程及已有评估产物  
> 分析日期：2026-08-19  
> 本文只给出分析、优化思路和实施步骤，不修改业务代码与测试代码。

## 1. 先理解：测试和评估不是一回事

本项目需要同时回答四个不同问题：

| 层次 | 要回答的问题 | 本项目对应内容 |
| --- | --- | --- |
| 单元测试 | 一个函数在固定输入下是否按契约工作？ | `test_import_document_services.py`、`test_query_services.py` 中的大部分用例 |
| 集成测试 | 多个节点、数据库和模型连接起来后是否能工作？ | 查询图 mock 测试；真实 Milvus 评估流程的一部分 |
| RAG 检索评估 | 应该找到的资料是否被召回并排在前面？ | `app/rag_eval/metrics.py`、`runner.py` |
| 最终答案评估 | 回答是否正确、忠于证据、引用完整且对用户有用？ | 当前基本缺失 |

“22 个测试全部通过”只能说明已覆盖的代码契约没有被破坏，不能说明 RAG 回答质量好。反过来，一次人工提问回答得不错，也不能说明代码边界、异常降级和数据契约可靠。

可以把完整质量链路理解为：

```text
测试数据质量
  -> 文档解析与切分
  -> metadata 与向量化
  -> 基础召回 / HyDE 召回
  -> RRF 融合
  -> Reranker 精排
  -> 上下文构造与引用
  -> 最终答案
  -> 延迟、成本、稳定性和安全性
```

前一层不可靠，后一层的分数就难以解释。因此评估不能只看一个总分，而要逐层定位。

## 2. 当前 tests 目录总体结论

当前共有 3 个测试文件：

| 文件 | 自动发现情况 | 主要作用 | 当前定位 |
| --- | --- | --- | --- |
| `tests/test_import_document_services.py` | 会被 `unittest` 发现，共 13 项 | 验证 metadata、切分、Embedding、Milvus 索引编排 | 单元测试为主 |
| `tests/test_query_services.py` | 会被 `unittest` 发现，共 9 项 | 验证过滤、RRF、Rerank、证据标签、无结果回答和查询图连接 | 单元测试 + 轻量图集成测试 |
| `tests/test_rag_eval_tester.py` | 文件会被扫描，但其中没有 `test_*` 用例 | 手工调用评估数据导入和批量评估 | 示例脚本，不是自动化测试 |

本次实际验证结果：

- `pytest` 无法运行，因为当前虚拟环境没有安装 `pytest`。
- 使用 `unittest discover`，关闭文件日志后共运行 22 项测试，结果全部通过。
- 如果不关闭文件日志，导入测试模块时会尝试向工作区外的 `rewater-agent-data-base/logs` 写文件，在受限环境中直接收集失败。
- 即使测试中的业务调用已经 mock，模块导入时仍尝试连接 MongoDB；本次连接失败带来了约 60 秒额外等待。
- 这 22 项用例不包含 `app/rag_eval` 指标函数、数据集、报告汇总和 runner 的断言测试。

结论是：项目已经有一组有价值的核心契约测试，但它还是“局部防回归网”，尚未形成可持续的完整评估体系。

## 3. `test_import_document_services.py` 解读

### 3.1 测试辅助数据

文件先定义了稳定的假数据：

- 固定 64 位 `DOCUMENT_ID` 和过期 `STALE_CHUNK_ID`；
- `_document_metadata()` 构造通过校验的 metadata；
- `_split_state()` 构造切分服务所需状态；
- `_embed_result()` 构造 1024 维 dense 向量和 sparse 向量。

这些辅助函数的原理是“用最小、确定、无外部依赖的数据替代真实模型结果”。这样测试关注业务契约，不会因为模型、网络或数据库波动而随机失败。

必要性：非常高。Agent/RAG 项目的模型和数据库都较慢且不稳定，核心纯逻辑必须能脱离外部服务快速验证。

### 3.2 MetadataServiceTest

当前 5 项测试验证：

1. metadata 上下文只取正文前 10000 字；
2. LLM 返回字段会归一化，重复值会去除，非法额外字段会丢弃；
3. `全国` 与具体地区不能同时出现；
4. 随机上传目录不应改变文档 ID；
5. metadata 提取最终只保留约定的最小字段。

测试原理：

- 用等值断言验证确定性转换；
- 用 `assertRaises` 验证非法输入必须失败；
- 用 `patch` 替代 LLM，只测试 LLM 结果进入系统后的处理逻辑；
- 用字段集合完全相等，防止旧字段或意外字段悄悄进入下游。

为什么必要：metadata 会进入过滤表达式、向量文本和索引 schema。一旦字段名称或规则漂移，常见结果不是立即报错，而是检索悄悄变差，因此契约测试比只看接口成功更重要。

当前不足：

- 只覆盖一个合法文档类型，没有系统覆盖空值、非列表、超长值、大小写、空白字符和完全非法类型。
- 只测试 `全国 + 深圳市`，没有覆盖其他特殊地区组合与层级冲突。
- 只证明两个随机目录得到相同 ID，没有证明不同文件、不同内容或同名不同来源应该如何区分。
- 截取前 10000 字只验证了现状，没有验证这种策略是否会漏掉文末发布日期、适用地区等重要 metadata。
- LLM 异常、超时、返回非 JSON、缺字段时的降级行为未覆盖。

优化步骤：

1. 先整理 metadata 输入输出契约表，明确每个字段的类型、是否必填、允许值和最大长度。
2. 为每条校验规则各设计“合法、边界、非法”三类用例。
3. 增加 LLM 返回空值、错类型、多余字段、格式错误和抛异常的用例。
4. 明确 document ID 的业务身份规则，再增加同名异内容、同内容异路径、重复导入用例。
5. 用带文首/文中/文末关键信息的样本评估 10000 字截断策略，而不是只把当前行为固定下来。

### 3.3 SplitServiceTest

当前 3 项测试验证：

1. Markdown 标题、普通正文、表格、代码能被识别为 `text/table/code`；
2. 最终 chunk 字段必须严格等于新契约，旧字段必须消失；
3. 超长文本会拆成多个不超过 1000 字的 chunk，且末尾内容没有被静默截断。

测试原理：把一小段同时包含多种结构的 Markdown 当成“微型文档”，检查切分结果的结构类型、字段和内容完整性。

为什么必要：切分是 RAG 的信息边界。切得过大影响召回精度，切得过小丢失上下文，表格或代码处理错误还可能让答案失真。

当前不足：

- 检查的是字符长度 `<= 1000`，而模型实际受 token 数限制；中英文、表格和代码的字符/token 比例不同。
- 只检查尾句存在，没有验证所有原文是否恰好保留一次，可能仍有中间丢失或重复。
- 没有覆盖多级标题路径、无标题文档、空文档、连续表格、超长表格、代码围栏异常、图片引用和 Markdown 嵌套。
- 没有评估 chunk overlap 是否足以保留跨边界语义。
- 没有把“切分质量”与后续召回结果关联起来。

优化步骤：

1. 建立切分样本文档矩阵，至少覆盖普通政策、技术标准、表格密集文档、代码/公式、图片和异常 Markdown。
2. 增加内容守恒检查：去除允许新增的标题上下文后，原始有效内容不能丢失，也不能无意重复。
3. 同时断言字符数和真实 tokenizer 的 token 数上限。
4. 增加标题层级、相邻 chunk overlap、表格完整性及空输入测试。
5. 用同一评测集比较不同 chunk size/overlap 的 Recall@K、MRR 和答案忠实度，再决定参数。

### 3.4 EmbeddingAndIndexServiceTest

当前 5 项测试验证：

1. Embedding 数量与 chunk 数一致，dense 维度为 1024，保留 sparse 向量并移除临时文本；
2. 模型失败时整批明确失败，不会静默跳过；
3. 入库记录会丢弃内部临时字段；
4. schema 不兼容时改用 `kb_chunks_v2`，避免破坏旧集合；
5. 更新文档时先 upsert 新 chunk，再移除过期 chunk。

测试原理：模型和 Milvus 都用 mock，只观察传入、返回、异常以及调用顺序。

为什么必要：向量数量错位会让内容与向量对应错误；静默跳批会形成不完整知识库；先删后写会在写入失败时丢数据；schema 直接覆盖可能造成不可恢复的数据损失。

当前不足：

- 没有测试 dense/sparse 数量不一致、维度错误、NaN/Inf、空向量和返回错类型。
- 没有覆盖多批次边界，例如 0、1、batch_size、batch_size+1 个 chunk。
- 只验证调用过，没有验证 upsert 失败时绝不能删除旧 chunk。
- 没有覆盖重复导入幂等性、部分失败、重试和并发导入。
- 没有验证索引 metric、向量维度、查询 metric 三者一致。
- 没有真实 Milvus 的最小集成测试，因此 mock 接口与实际 SDK 漂移时不一定能发现。

优化步骤：

1. 增加 Embedding 返回结构和数值合法性测试。
2. 用参数化思想覆盖批次边界和多批次失败位置。
3. 明确“先写成功，再删除”的事务语义，覆盖 upsert 失败、删除失败和重试。
4. 增加一个使用临时测试集合的 Milvus 集成测试，验证 schema、metric、upsert、查询和清理。
5. 将模型名、版本、维度、metric 作为评估运行元数据保存并做一致性检查。

## 4. `test_query_services.py` 解读

### 4.1 辅助对象

`_local_candidate()` 构造统一的本地检索候选；`_FakeTokenizer` 和 `_FakeReranker` 用确定分数替代真实精排模型。

好处是结果稳定、速度快，也能精确验证字段契约。局限是模拟器过于理想，不会暴露真实 tokenizer 截断、模型批次限制、显存不足和分数分布变化。

### 4.2 过滤表达式测试

`test_filter_expression_uses_new_schema` 验证：

- 旧字段 `item_name` 不再进入表达式；
- 新字段 `document_type`、`region_names` 会进入表达式；
- 地区会兼容 `全国`；
- 非法文档类型会被过滤。

必要性：过滤条件一旦构造错误，向量相似度再高也找不到正确文档。

不足与优化步骤：

1. 增加空过滤、仅软过滤、严格模式、多个值组合测试。
2. 增加引号、反斜杠和特殊字符，验证 Milvus 表达式转义与注入安全。
3. 验证所有字段都非法时是降级为空过滤还是明确失败。
4. 用真实 Milvus 临时集合验证表达式语法确实可执行。

### 4.3 本地候选与 RRF 测试

`test_local_candidate_and_rrf_contract` 验证普通召回与 HyDE 命中同一 `chunk_id` 时会合并成一条，并记录两个来源。

RRF 的基本原理是只利用各检索器中的名次进行融合，常见形式为：

```text
RRF_score(d) = Σ source_weight / (k + rank_source(d))
```

它适合融合分数尺度不同的检索结果，因为 dense、sparse 或 HyDE 的原始分数不必直接可比。

当前不足：只测试“同一条、双路重复”的最简单情况，没有验证实际公式、权重、排序、单路为空、不同文档、重复 ID、并列名次和 top-k 截断。

优化步骤：

1. 手工构造 3～5 条候选，先在纸面计算预期 RRF 分数。
2. 分别覆盖单路、双路、一路为空、重复候选和权重变化。
3. 断言最终顺序、来源集合、原始检索分数保存和 top-k。
4. 增加性质测试：同一文档在更多检索路排位靠前时，融合分数不应下降。

### 4.4 Reranker 测试

现有测试验证：

- 只有本地候选、没有 Web 结果时仍可精排；
- 本地与 Web 使用相同的标题和正文构造精排文本；
- 假模型返回 0.9 时结果 score 更新为 0.9。

必要性：这保证查询不依赖 Web 才能回答，并避免不同来源因拼接格式不同受到不公平排序。

当前不足：

- 没有验证候选超过 token 限制时的截断边界。
- 没有验证模型返回单个标量、数量不一致、NaN、异常和空候选。
- 没有验证阈值、相邻分差、最大保留数和排序稳定性。
- 只断言统一 `score`，但不同阶段复用同一字段会使原始召回分、RRF 分和 rerank 分含义混淆。
- 没有用真实 reranker 做小规模质量基准。

优化步骤：

1. 为所有模型返回形态和异常路径补契约测试。
2. 为 token 截断、批次大小、阈值和 top-k 补边界测试。
3. 在评估报告中分开记录 retrieval、RRF、rerank 分数，不用一个字段解释全部阶段。
4. 建立 30～50 个人工标注的正负文本对，评估真实 reranker 的 MRR/nDCG 与版本回归。

### 4.5 答案证据与来源标签测试

现有 4 项相关测试验证：

- 证据上下文使用可读来源标签，不暴露所谓“置信度”；
- 普通向量召回和 HyDE 的本地来源标签统一；
- Web 来源使用 URL；
- LLM 仍输出旧式 `[来源1]` 时会替换成新标签；
- 无检索结果时返回固定答案并且图片列表为空。

必要性：检索分数不是事实置信度，直接展示容易误导用户；统一引用能提高可追溯性；无证据时拒答比编造更安全。

当前不足：

- 没有验证多个引用、引用越界、重复引用、无引用、恶意 URL 和缺标题字段。
- 只检查标签字符串，没有检查回答中的每个事实是否真的被对应证据支持。
- 无结果只覆盖完全空列表，没有覆盖“有候选但都低于阈值”。
- 没有覆盖流式回答、图片证据、历史保存失败和 LLM 生成异常。

优化步骤：

1. 增加引用映射的完整边界测试和 URL/文本转义测试。
2. 定义引用完整率：需要证据的事实中，有有效引用的比例。
3. 定义引用正确率：引用文段确实支持相邻结论的比例。
4. 增加无结果、低相关结果、模型异常和历史写入异常的降级用例。
5. 用人工标注或受控 LLM judge 评估忠实度，同时保留人工抽检。

### 4.6 查询图状态契约测试

`test_query_graph_state_contract` 把查询理解、三路召回、Rerank 和答案节点全部 mock，只运行真实 LangGraph 编排，验证：

- 三路并行节点可以汇入 RRF；
- RRF 结果能进入 Rerank；
- 最终可以到达答案节点并返回答案。

这类测试很必要，因为节点各自正确不代表图的边、路由和并行状态合并正确。

它没有证明的内容：

- 每个节点的真实实现是否能协同；
- 并行节点某一路失败时是否能降级；
- 查询需要澄清时的短路路径；
- state key 冲突、并发更新和空结果路径；
- 流式输出、API 层和历史存储。

优化步骤：

1. 保留当前“全 mock 图连通性测试”，让它继续快速防止编排断裂。
2. 增加澄清短路、一路失败、两路失败、全空、节点异常等路由用例。
3. 再增加少量“只 mock 外部边界”的图集成测试，让真实 service/node 共同运行。
4. 最后增加 API 到图的端到端冒烟测试，验证请求 schema、SSE/响应和错误码。

## 5. `test_rag_eval_tester.py` 与 `app/rag_eval` 解读

### 5.1 为什么它不是自动测试

虽然文件名以 `test_` 开头，但内部函数叫：

- `run_insert_test_data()`；
- `run_eval()`；
- `demo()`。

它们既不是 `unittest.TestCase` 的 `test_*` 方法，也不是模块级 `test_*` 函数，因此自动发现时不会执行。这个文件本质上是手工入口示例。

必要性：作为初学者的最小调用示例有价值。  
不足：放在 `tests` 下容易让人误以为 CI 已经覆盖 RAG 评估，而且没有阈值断言，评估结果再差也不会让测试失败。

优化步骤：

1. 在项目约定中明确它是手工评估入口，不计入自动测试数量。
2. 将“指标计算正确性”做成无外部依赖的自动单元测试。
3. 将“真实数据入库与真实检索评估”标记为单独的慢速集成评估。
4. 为批量报告定义最低门槛，低于门槛时明确失败，而不是只生成 JSON。

### 5.2 评估包各文件职责

| 文件 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `dataset.py` | 构造 8 个 HAK 180 知识 chunk、2 个问题和标注 | 入库后的 chunk ID | JSON 题库 |
| `metrics.py` | 提取 ID，计算主体命中率、precision、recall、must-hit rate | 查询 state + 标注 | 单题分层指标 |
| `runner.py` | 数据入库、逐层执行查询、汇总并写报告 | 题库、Milvus、Embedding、Reranker | 详细结果、汇总、报告路径 |
| `tester.py` | 对外提供两个简单方法并关闭 Mongo 客户端 | 无 | 入库结果或评估结果 |

### 5.3 当前评估运行流程

准备阶段：

1. `build_import_chunks()` 构造 8 条 HAK 180 演示知识。
2. `insert_batch_eval_dataset()` 构造导入 state。
3. mock 主体识别，使主体固定为 `HAK 180`。
4. 真实执行向量化与 Milvus 入库节点。
5. 从 Milvus 查询真实 `chunk_id`。
6. 按这些 ID 生成 2 条带 gold/must-hit 标注的问题。

评估阶段：

1. 读取题库。
2. 把问题原文同时作为 `original_query` 和 `rewritten_query`。
3. 直接把标准主体写入 state，并用文件标题做严格过滤。
4. 把 HyDE 输出固定为同一句话。
5. 执行普通检索、HyDE 检索、RRF 和 Rerank。
6. 分别读取四层 state，与 gold ID 做集合比较。
7. 对两道题的指标做算术平均并写入 JSON 报告。

### 5.4 现有指标怎么理解

假设标准相关 chunk 是 `{A, B, C, D}`，系统返回 `[A, X, B]`：

- Precision = 命中数 / 返回数 = 2 / 3；含义是“找回来的内容有多干净”。
- Recall = 命中数 / 标准相关数 = 2 / 4；含义是“该找的内容找全了多少”。
- 若 must-hit 是 `{A, C}`，Must-hit rate = 1 / 2；含义是“不可遗漏的关键证据找到了多少”。
- 主体命中率 = 预测主体与标准主体交集数 / 标准主体数。

这些指标有必要，但当前实现把结果当成集合，只关心“有没有”，不关心“排第几”。把关键证据排第 1 和排第 100 会得到相同 Recall；对真实 RAG 而言二者差别很大，因为最终上下文通常只取前几条。

### 5.5 当前评估最严重的问题

#### 问题 1：题库规模和领域不合适

目前只有 8 个设备说明 chunk、2 道高度相似的问题，且主题是 HAK 180 烫印设备，不是本项目当前的再生水政策/技术知识场景。

这只能验证链路演示，不能代表生产质量。两个样本的平均值也极不稳定：任意一道题的成败都会使平均值大幅变化。

改进步骤：

1. 先从真实再生水使用场景定义问题分类。
2. 每类先做 10～20 道，第一阶段达到至少 100 道。
3. 覆盖事实查询、条件过滤、表格数值、多文档综合、时间/地区冲突、无答案、模糊问题和对抗问题。
4. 按简单/中等/困难和单跳/多跳打标签。
5. 题目与 gold 由领域人员复核，避免开发者自问自答造成偏差。

#### 问题 2：gold `chunk_id` 会失效，现有报告已出现证据

当前题库文件中的 ID 与已有报告中用于评分的标准 ID 不一致；报告实际召回了另一组新 ID，所以四层指标全部被算成 0。最可能的原因是重新入库后生成了新 ID，但题库或报告没有以同一次数据快照为准。

这意味着当前 0 分不能直接解释为检索失败，它首先是评估数据版本一致性失败。

改进步骤：

1. 为每次评估生成唯一 `dataset_version` 和 `run_id`。
2. 题库、入库数据、报告必须记录同一数据版本、collection、模型版本和生成时间。
3. 在正式算分前做预检：每个 gold ID 必须能在目标 collection 查到，否则整次评估标记为无效，不输出质量结论。
4. 优先使用内容稳定哈希作为 chunk 身份；若使用数据库自增 ID，则保存“稳定业务 ID -> 本次数据库 ID”的映射。
5. 不覆盖旧报告；按 run_id 保存，保证结果可追溯。

#### 问题 3：主体识别指标当前没有实际评估意义

`run_query_eval_case()` 直接把 `expected_item_names` 写入 state，之后 `metrics.py` 又拿 state 中的 `item_names` 与 expected 比较。因此主体命中率天然是 1.0，并没有运行真实主体识别。

而当前查询 state 已把 `item_names` 标为旧兼容字段，新查询主要依赖 `query_filters`。这也说明评估指标与新版查询契约存在漂移。

改进步骤：

1. 决定新版真正要评估的是主体识别，还是 region/document_type/topics 等过滤解析。
2. 如果评估查询理解，就必须运行真实查询理解节点，再比较结构化过滤字段。
3. 为多值字段分别计算 exact match、micro/macro precision、recall、F1。
4. 如果不再使用主体识别，应从质量看板移除该指标，避免 1.0 造成虚假安全感。

#### 问题 4：只评估检索，不评估最终答案

当前流程到 `reranked_docs` 就结束，没有调用最终回答生成。因此无法回答：

- 答案是否正确；
- 是否遗漏关键条件；
- 是否出现无证据编造；
- 引用是否真的支持结论；
- 无答案问题是否正确拒答。

改进步骤：

1. 给评测集增加参考答案、关键事实点和允许的表达变体。
2. 运行完整回答节点，保存答案、引用、证据、prompt 和模型版本。
3. 优先增加可规则化指标：关键事实覆盖率、数字/单位一致率、引用有效率、拒答准确率。
4. 再增加 LLM judge 的 correctness、faithfulness、relevance 评分，并固定 judge 模型和 rubric。
5. 每次版本变更人工抽检失败样本；不能只信另一个 LLM 的分数。

#### 问题 5：指标不考虑排序

当前 precision/recall 对整层返回列表做集合比较，没有 K，也没有排名折扣。

改进步骤：

1. 至少增加 Hit@1/3/5、Precision@K、Recall@K。
2. 对“第一个相关结果出现位置”增加 MRR。
3. 对有多个相关等级的结果增加 nDCG@K。
4. Rerank 前后用同一 K 比较，确认精排确实把好结果向前移动，而不是仅改变分数。

#### 问题 6：固定 HyDE 文本可能造成偏置

两道问题都使用同一个、且直接包含关键答案的 HyDE 文本。这提高了可重复性，却不能评估 HyDE 生成质量，也可能人为放大 HyDE 召回效果。

改进步骤：

1. 把评估拆为“固定 HyDE 的检索算法回归”和“真实 HyDE 的端到端质量”两套。
2. 固定模式为每道题保存各自的 HyDE 基准文本，不能所有题共用一句。
3. 真实模式重复运行多次，报告均值、标准差和失败率。
4. 与“不使用 HyDE”的 baseline 做成对照实验，只有显著提升才保留复杂度。

#### 问题 7：环境检查只检查配置，不检查服务健康

`insert_env_ready()` 和 `batch_eval_ready()` 只看配置字符串是否非空，不代表模型文件能加载、Milvus 能连接、collection 存在或维度匹配。

同时，当前 `runner.py` 的客户端调用方式存在明显静态风险：一处用 `milvus_gateway.client()`，入库处却把 `milvus_gateway.client` 方法本身赋给变量；随后会对它调用 `.query()`。此外 runner 使用的 item collection 属性名也需要与 gateway 当前公开属性逐项核对。这些问题应在 runner 自动测试中被提前发现。

改进步骤：

1. 将配置完整性、服务连通性、collection/schema、模型加载分成四层预检。
2. 每层返回明确错误，不用单个布尔值隐藏原因。
3. 为 runner 注入 fake gateway，自动验证客户端获取方式、collection 属性名和查询参数。
4. 任何预检失败都应终止本次 run，并标记为环境失败，而不是生成 0 分质量报告。

#### 问题 8：没有延迟、成本、稳定性和回归门槛

当前报告只有质量均值，没有每层耗时、token、模型调用次数、失败率，也没有“什么分数才算通过”。

改进步骤：

1. 记录每题及每节点 p50/p95 延迟、模型 token、调用次数和估算成本。
2. 对非确定模型重复运行，记录均值、标准差和最差值。
3. 建立当前主分支 baseline，不只看绝对分，也看相对退化。
4. 设两类门槛：关键安全指标不得低于绝对值；普通质量指标不得相对 baseline 明显下降。
5. 报告按问题标签分组，避免总体平均值掩盖某一类问题完全不可用。

## 6. 当前测试体系的其他共性不足

### 6.1 测试隔离不完整

测试导入阶段会初始化日志和 MongoDB。结果是：

- 只想测纯函数，也可能因为日志目录权限失败；
- Mongo 不可达时，要等待连接超时；
- CI 成败受开发环境 `.env` 影响。

优化步骤：

1. 定义独立 test 配置，默认关闭文件日志、真实 Mongo、Milvus、MinIO 和模型加载。
2. 外部客户端使用惰性初始化，不在模块 import 时连接。
3. 单元测试只通过依赖注入/fake 使用外部接口。
4. 需要真实服务的用例单独标记为 integration/eval，并在环境具备时运行。

### 6.2 缺少测试工具链约定

`pyproject.toml` 没有声明 pytest、coverage 或测试配置；当前主要使用 `unittest`，但文件命名又接近 pytest 习惯。

优化步骤：

1. 团队先选择统一入口：继续 `unittest`，或引入 pytest 作为 runner；不要让两种命令产生不同收集结果。
2. 在 README/贡献指南中写明一键命令、环境变量、测试分类和预期耗时。
3. 增加覆盖率报告，但把覆盖率当“未测试代码提示”，不把高覆盖率等同于高质量。
4. CI 分成快速单元测试、服务集成测试、离线 RAG 评估三条任务。

### 6.3 缺少 API、安全和失败路径测试

当前没有覆盖 HTTP schema、上传、SSE、超时、并发、路径安全、提示词注入和敏感信息输出。

优化步骤：

1. 对导入/查询 API 增加成功、参数错误、超时和内部错误映射测试。
2. 增加文件名、路径穿越、超大文件和不支持类型测试。
3. 增加“文档内恶意指令”和“用户提示词注入”用例，检查系统是否把知识文本当命令执行。
4. 检查日志和返回值不泄露密钥、内部路径、完整 prompt 或不该展示的用户历史。

## 7. 本项目推荐的完整评估流程

下面是一套从零开始、适合本项目逐步落地的流程。不要一开始追求几十个指标，先让数据可信、链路可复现。

### 阶段 0：明确目标和发布门槛

1. 写出目标用户：例如设计人员、政策查询人员、运维人员。
2. 写出核心任务：地区政策查询、技术指标查询、操作步骤、跨文档综合、无答案拒答等。
3. 为每类任务定义最严重错误，例如数字答错、地区串用、无依据编造。
4. 定义首版最低门槛，例如关键证据 Hit@5、答案关键事实覆盖率、引用正确率、拒答准确率。

产物：`evaluation_spec`，包括任务分类、风险、指标和通过标准。

### 阶段 1：建立可信评测集

1. 从真实文档和真实用户问题采样，不只让开发者编题。
2. 清理隐私和敏感数据。
3. 给每题标注：问题、标签、难度、适用过滤条件、gold 文档/chunk、must-hit 证据、参考答案、关键事实点、是否应拒答。
4. 至少由第二个人复核 gold；争议题先移出发布门槛集。
5. 划分开发集和固定回归集，避免反复针对所有题调参造成过拟合。
6. 给数据集加版本号，提交变更说明。

建议首版分布：

| 类型 | 建议数量 | 关注点 |
| --- | ---: | --- |
| 单文档事实/条款 | 20 | 基础召回与精确回答 |
| 地区、文档类型等过滤 | 15 | query understanding 与过滤表达式 |
| 表格、数字、单位 | 15 | 切分完整性和数值正确性 |
| 多文档/多证据综合 | 15 | 多跳召回和上下文整合 |
| 同义改写、口语、错别字 | 10 | query rewrite 和鲁棒性 |
| 无答案/越界问题 | 15 | 拒答与防幻觉 |
| 冲突、过期、对抗问题 | 10 | 来源选择、安全与时效 |

### 阶段 2：固定运行环境和数据快照

1. 记录 Git commit、数据集版本、文档快照、collection 名称和 schema。
2. 记录 Embedding、Reranker、生成模型和 judge 模型的精确版本。
3. 记录 chunk size、overlap、top-k、RRF 权重、阈值、prompt 版本。
4. 评估前运行健康检查和 gold ID 存在性检查。
5. 生成唯一 run_id，所有中间结果都带该 ID。

产物：可复现的 run manifest。没有 manifest 的分数不要用于版本比较。

### 阶段 3：先运行快速自动测试

顺序建议：

1. 纯函数与数据契约测试；
2. 节点测试；
3. 图路由与并行合并测试；
4. API schema 和错误处理测试；
5. 外部客户端 contract 测试。

若这一阶段失败，应先修代码正确性，不要继续跑昂贵的质量评估。

### 阶段 4：验证导入质量

对固定文档快照检查：

1. 文档解析成功率；
2. 文本/表格/代码/图片内容保存率；
3. chunk 数、token 长度分布、过短/过长比例；
4. metadata 字段完整率和准确率；
5. Embedding 数量、维度和数值合法性；
6. 重复导入幂等性、旧 chunk 清理和索引 schema 一致性。

如果导入数据不可信，召回分数没有诊断价值。

### 阶段 5：逐层离线检索评估

对每道题保存各层完整候选和分数：

1. 普通混合检索；
2. HyDE 检索；
3. RRF 融合；
4. Reranker 精排。

每层计算：

- Hit@1/3/5；
- Precision@3/5；
- Recall@3/5；
- MRR；
- nDCG@5（有相关等级时）；
- must-hit@K。

分析原则：

- 普通召回差：优先看切分、Embedding、过滤和索引 metric。
- 普通召回好、HyDE 差：检查 HyDE prompt 或考虑关闭 HyDE。
- 两路都好、RRF 变差：检查权重、去重和 top-k。
- RRF 好、Rerank 变差：检查拼接文本、token 截断、模型或阈值。

### 阶段 6：评估最终答案

每道题运行到最终回答，保存答案和实际引用证据，评估：

1. 正确性：是否回答了问题且结论正确；
2. 关键事实覆盖率：参考答案的必要事实覆盖了多少；
3. 忠实度：回答中的事实是否都能由给定证据推出；
4. 引用正确率与完整率；
5. 无答案拒答准确率；
6. 数字、单位、地区、日期一致性；
7. 表达相关性与简洁度。

建议使用“规则 + 人工 + LLM judge”组合：数字和引用尽量用规则；高风险结论人工复核；开放表达再用固定 rubric 的 judge 扩展规模。

### 阶段 7：评估非功能质量

1. 每节点和端到端 p50/p95 延迟；
2. 模型 token 和估算成本；
3. 外部服务失败率、重试次数和降级成功率；
4. 相同问题多次运行的结果波动；
5. 并发下的吞吐、超时和 state 隔离；
6. 日志、监控、trace 是否能定位到失败节点。

### 阶段 8：做对照实验，而不是凭感觉调参

每次只改变一个主要变量，例如：

- chunk size/overlap；
- 是否使用 HyDE；
- dense/sparse 权重；
- RRF k/权重；
- reranker 模型或 top-k；
- prompt 版本。

同时比较总体和分组指标、延迟与成本。若质量提升只发生在开发集、不发生在固定回归集，应警惕过拟合。

### 阶段 9：形成发布门禁与失败样本闭环

1. 快速单元测试必须全部通过。
2. 关键安全指标必须达到绝对门槛。
3. 主要质量指标不得相对 baseline 明显下降。
4. 每次失败按“数据、导入、召回、融合、精排、生成、环境”分类。
5. 修复真实失败后，把该问题沉淀为新的回归样本。
6. 报告保留 run manifest、分组指标、失败案例和版本对比。

最终闭环是：

```text
线上/人工发现失败
  -> 复现并定位层级
  -> 修正数据、算法或提示词
  -> 增加回归用例
  -> 离线评估确认改善
  -> 灰度观察
  -> 纳入新 baseline
```

## 8. 推荐实施优先级

### P0：先让现有结果可信

1. 明确统一测试入口和测试环境，隔离日志/Mongo 等 import 副作用。
2. 给 `metrics.py`、`dataset.py`、`runner.py` 增加自动断言测试。
3. 修正并测试 runner 的 Milvus 客户端与 collection 接口契约。
4. 增加 gold ID 存在性和数据版本预检，禁止错版本报告被当作质量结论。
5. 将当前 HAK 180 的 2 题报告明确标为演示，不作为项目验收依据。

### P1：建立最小可用的再生水评测基线

1. 建立至少 100 题、覆盖 7 类场景的领域评测集。
2. 增加查询理解、过滤、检索排序和最终答案指标。
3. 增加无答案、地区冲突、数值/单位和多文档问题。
4. 保存 run manifest，建立第一版 baseline 与发布阈值。

### P2：提高诊断力和工程可靠性

1. 增加真实 Milvus、Mongo、API 的小规模集成测试。
2. 增加失败降级、超时、并发、流式输出和安全测试。
3. 增加延迟、成本、稳定性以及按标签分组的看板。
4. 建立固定对照实验流程，评估 HyDE、RRF 和 Reranker 的真实增益。

### P3：持续评估

1. 从真实用户反馈中持续补充困难样本。
2. 定期复核过期政策、冲突来源和数据漂移。
3. 对关键问题做人工抽检和线上灰度评估。
4. 只有在数据版本、模型版本和参数都可追溯时，才比较跨版本分数。

## 9. 初学者执行检查表

每次准备发布前，可以按下面顺序逐项确认：

- [ ] 我知道这次改动影响导入、召回、精排还是回答层。
- [ ] 单元测试不需要真实外部服务即可快速运行。
- [ ] 测试收集数量符合预期，不存在“文件叫 test 但没有运行”的情况。
- [ ] 真实服务集成测试使用独立测试数据和 collection。
- [ ] 题库、索引和报告使用同一个 dataset_version/run_id。
- [ ] 所有 gold chunk 在本次评估 collection 中真实存在。
- [ ] 检索同时看 @K、排序指标和 must-hit，不只看一个平均 Recall。
- [ ] 最终答案检查正确性、忠实度、引用和拒答。
- [ ] 报告记录模型、prompt、参数、Git commit、延迟和成本。
- [ ] 与固定 baseline 比较，并查看分组失败样本。

## 10. 最终评价

现有 `tests` 的优点是：已经开始围绕新字段契约、失败不静默、非破坏性索引更新、无 Web 降级、引用格式和 LangGraph 并行汇合建立保护网。这些测试方向是正确的，22 项自动测试也能在隔离文件日志后通过。

当前最大短板不在“完全没有测试”，而在四点：

1. 自动测试覆盖仍集中在少数 happy path 和契约点，外部依赖隔离不完整；
2. `test_rag_eval_tester.py` 只是手工入口，评估包自身没有自动断言保护；
3. 现有评测集只有 2 题且领域不匹配，gold ID 还出现版本失配，因此报告的 0 分不能代表真实检索质量；
4. 当前只评估检索集合命中，不评估排名、最终答案、引用忠实度、延迟、成本和稳定性。

最合适的推进方式是先完成 P0，让每次评估的数据和运行都可信；再用真实再生水场景建设 P1 基线。只有评测集、数据版本和指标含义都稳定后，调 chunk、HyDE、RRF 或 Reranker 参数才有可靠依据。
