# rewater-agent 项目上下文

## 1. 文档目的

本文用于统一项目定位，避免把当前代码中的“商品识别 Agent”业务误认为最终业务。后续需求分析、架构设计和代码修改必须同时区分：

- 当前代码状态：仓库现在真实存在、可以从代码确认的能力。
- 目标业务状态：面向再生水行业的垂直领域知识库 Agent。
- 迁移工作：从当前实现演进到目标状态所需的重构、替换和补充。

## 2. 项目来源与当前迁移状态

rewater-agent 来源于一套商品/设备识别知识库 Agent 代码。当前仓库已经包含文档导入、混合向量检索、会话历史、联网搜索、重排和答案生成等通用 RAG 基础，但查询入口仍以 `item_name`（商品或设备主体）识别和确认作为核心前置条件。

项目当前处于业务迁移早期：

- 项目名称已经调整为 rewater-agent。
- 通用基础设施和两条 LangGraph 工作流已经存在。
- 再生水行业的分类体系、地域体系、专业主题体系及 metadata 契约尚未落地。
- 当前商品主体集合、商品确认阈值和按商品过滤检索仍是主要业务路径。
- 查询相关模块存在接口名称和返回契约不一致，当前状态不能视为稳定基线。
- README 及部署、数据治理说明仍不完整。

因此，当前代码应被视为“可复用技术底座 + 待替换的旧业务实现”，而不是最终产品实现。

## 3. 最终目标

构建面向再生水行业的专业知识查询与辅助决策 Agent，为以下用户提供可信、可追溯的行业知识服务：

- 水务企业技术和运行人员；
- 规划、咨询和工程设计人员；
- 政府管理、政策制定与行业监管人员；
- 科研与技术研究人员。

重点知识类型包括：

1. 法规政策；
2. 标准规范；
3. 规划文件；
4. 科研论文；
5. 技术研究报告。

核心知识维度至少包括：

- 地域：国家、省、市、区等层级，重点覆盖广东省、深圳市及深圳各区；
- 专业方向：水质标准、工艺技术、工程设计、运行维护、管理要求、经营政策等；
- 文档效力与时效：发布机构、发布日期、实施日期、有效状态、替代关系；
- 来源与证据：原文、页码、章节、发布机构和可访问地址。

### 3.1 项目建设重点

本项目定位为高质量 AI Agent 应用工程，而不是完整的企业 SaaS 平台。当前建设重点是：

1. Agent Workflow 设计：使用 LangGraph 构建清晰、可调试、可扩展的工作流；
2. RAG 架构能力：覆盖知识导入、结构化切分、召回、融合、重排和答案生成；
3. Hybrid Retrieval 能力：结合 Dense、Sparse 和 metadata filter；
4. Query Understanding 能力：理解地域、文种、专业主题、时效和查询意图；
5. 行业知识库建设能力：形成适合再生水资料的分类、metadata 和 chunk 方案；
6. 工程化能力：具备配置、日志、测试、评估、异常处理和可重复部署能力。

### 3.2 当前非核心范围

以下内容不进入当前核心架构，只作为未来应用深化方向：

- 用户认证；
- RBAC 权限；
- 多租户；
- 完整的文档版本管理；
- 人工审核与发布流程；
- 长期 Memory 系统；
- 企业级监控平台。

领域资料本身的标准号、发布日期、生效状态和替代关系仍属于检索所需知识 metadata，不等同于建设完整的文档版本管理系统。

## 4. 业务价值

- 缩短法规、标准、规划和技术资料的查找时间。
- 支持跨地域、跨文档类型的规范对照和差异分析。
- 为设计选型、运行维护和管理决策提供带出处的知识依据。
- 沉淀深圳及广东地区高密度知识，同时保留全国资料的统一检索能力。
- 通过文件日期、效力状态和来源信息降低使用过期或低可信资料的风险。
- 为后续工具型 Agent 能力提供知识底座，例如标准比对、指标核查和专题报告辅助生成。

## 5. 当前项目结构与模块组成

```text
app/
├── api/           HTTP 接口与 Pydantic 请求响应模型
├── process/       导入、查询 LangGraph 及节点适配层
├── rag/           导入和查询领域服务
├── infra/         LLM、Milvus、MongoDB、MinIO、MinerU 适配层
├── shared/        配置、底层客户端、模型加载、日志和公共工具
├── resources/     Prompt 模板与演示页面资源
└── rag_eval/      检索评估数据、指标和批量评估流程
```

当前 Agent 框架包含两条 LangGraph：

- 导入图：文件识别 → PDF 转 Markdown → 图片增强 → 文档切分 → 商品主体识别 → Embedding → Milvus 入库。
- 查询图：商品主体确认/问题改写 → 普通检索、HyDE、联网搜索 → RRF → Rerank → 答案生成。

当前数据库与存储：

- Milvus：商品主体向量集合和 chunk 向量集合；
- MongoDB：会话历史；
- MinIO：Markdown 图片；
- 本地文件系统：上传文件、MinerU 解析结果和切分备份。

当前模型调用方式：

- OpenAI 兼容接口通过 LangChain `ChatOpenAI` 调用文本和视觉模型；
- BGE-M3 本地生成稠密、稀疏向量；
- FlagEmbedding `FlagReranker` 本地执行交叉编码重排；
- DashScope MCP 提供联网搜索；
- MinerU 服务负责 PDF 结构化解析。

## 7. 商品业务相关代码

以下内容属于当前来源项目的业务实现，不应延续为目标业务核心：

- `item_name` 作为查询必须先确认的唯一知识主体；
- `item_name_collection` 商品主体向量集合；
- 导入时调用 LLM 识别单一商品/设备名称；
- 查询时以固定相似度区间确认商品或向用户提供商品候选；
- chunk 文本拼接“主体 + 内容”后生成向量；
- 仅通过 `item_name` 过滤知识片段；
- 以同一 `item_name` 删除旧 chunk 的覆盖逻辑；
- 商品识别和商品确认 Prompt；
- 以 HAK 180 烫金机为中心的测试数据和评估产物。

这些实现未来应删除或替换，但在新的 metadata、检索和迁移测试准备完成前，不宜直接物理删除。

## 8. 已确认边界与待确认事项

- 首阶段暂不建设知识自动更新机制。
- 首阶段不建设法规、标准的人工审核发布流程；效力状态作为可检索 metadata 使用。
- 当前没有企业内部资料和复杂访问权限需求。
- 部署目标为云服务，预期并发较低，暂不设置严格的响应时间、模型预算和保密等级指标。
- 允许使用联网搜索，但结果必须保留并确认来源，且与本地知识库证据明确区分。
- 是否需要表格数值精确计算、单位换算或结构化数据库查询仍待确认。
