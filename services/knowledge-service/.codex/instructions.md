# rewater-agent Codex 工作约束

## 项目定位

1. 当前项目处于从商品识别 Agent 向再生水行业知识库 Agent 迁移的阶段。
2. 不得默认当前代码中的商品、设备、`item_name` 或 HAK180 业务就是目标业务。
3. 回答和设计时必须区分：当前真实实现、目标规划、迁移步骤。
4. 对仓库中无法确认的业务规则、数据来源、权限和部署条件标记“待确认”，不得虚构模块或完成状态。
5. 项目目标是高质量 AI Agent 应用工程，核心展示 Agent Workflow、RAG、Hybrid Retrieval、Query Understanding、行业知识库建设和必要工程化能力，不按完整企业 SaaS 平台设计。
6. 用户认证、RBAC、多租户、完整文档版本管理、审核发布流程、长期 Memory 和企业级监控平台只作为未来规划，不加入当前核心架构或主迁移路线。

## 修改规则

1. 修改代码前先检查调用链、state、配置、数据 Schema、测试和外部依赖的影响范围。
2. 大规模重构、删除旧业务或迁移数据库前，先提出迁移方案、兼容策略、回滚方式和验证方法。
3. 优先保留并修复可复用的 Agent 基础能力：LangGraph 编排、工具调用、LLM Provider、Embedding、Hybrid Retrieval、Rerank、数据库封装、配置、日志、SSE 和评估框架。
4. 商品业务逻辑应有计划地替换；在新链路与回归测试就绪前，不直接删除旧实现和数据。
5. 每次修改只解决一个清晰问题，避免在同一变更中混合无关重构。
6. Agent 节点和 service 的返回契约必须明确，不混用完整 state、state 增量和纯业务结果。
7. 新增目标架构能力时，应采用再生水领域的文种、地域、主题、时效、来源和证据模型，不用 `item_name` 换名冒充行业模型。
8. 不覆盖用户已有的未提交修改，不执行未经明确授权的破坏性操作。

## 测试与交付

1. 每次代码修改后必须说明测试方法、实际执行结果和未覆盖风险。
2. 优先补充不依赖真实外部服务的单元测试和节点契约测试；集成测试明确列出所需的 Milvus、MongoDB、MinIO、MinerU、LLM 或 MCP 条件。
3. 修改 RAG 策略时，应说明对导入数据、Milvus Schema、检索结果和离线评测的影响。
4. 修改 Prompt、Chunk、Embedding、融合或 Rerank 时，应使用行业评测集比较前后结果；评测集未建立时明确标记该限制。
5. 最终交付说明至少包含：变更文件、完成内容、验证结果、兼容性或迁移注意事项。
