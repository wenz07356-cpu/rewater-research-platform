# Query V5：面向 Precision / Recall 偏好的交互式检索方案

## 1. 结论

该方案可行，而且当前 Query 链路已经具备形成多模式检索的大部分基础能力。现有流程为：

> 查询理解 → 普通 BGE-M3 混合检索 + HyDE 检索 + Web 检索并行执行 → 加权 RRF → BGE Reranker 动态截断 → 生成答案

当前主要限制不是算法能力不足，而是检索参数均为模块级常量，所有请求只能共用同一套配置。后续实现时，应把“请求级检索配置”放入 Query state，由请求入口解析模式并生成一份不可变的有效配置；不能在请求处理中临时修改全局常量，否则并发请求会互相污染。

建议前台提供四种模式：

1. **均衡模式**：完全保持当前行为，作为默认模式。
2. **精确回答模式**：减少弱相关上下文，优先提升 Context Precision。
3. **全面检索模式**：扩大候选和最终上下文，优先提升 Context Recall。
4. **自定义模式**：允许用户在安全范围内调整少数可理解参数。

前台名称不建议直接只写“高 Precision / 高 Recall”。普通用户更容易理解“精确回答（材料更少、更聚焦）”和“全面检索（材料更多、更完整）”。

## 2. 当前链路与基线

### 2.1 当前固定参数

| 阶段 | 当前参数 | 当前值 | 作用 |
|---|---|---:|---|
| 混合检索 | `SEARCH_ANN_LIMIT` | 20 | 稠密、稀疏单路 ANN 候选上限 |
| 混合检索 | `SEARCH_TOP_K` | 10 | 普通检索和 HyDE 检索各自最终返回数量 |
| 混合检索 | `DENSE_WEIGHT` | 0.6 | 语义稠密向量权重 |
| 混合检索 | `SPARSE_WEIGHT` | 0.4 | 关键词稀疏向量权重 |
| HyDE | 是否启用 | 当前固定启用 | 生成假设性文档表述，通常有利于召回 |
| HyDE | `HYDE_MAX_CHARS` | 300 | HyDE 文本长度上限 |
| Web | 是否启用 | 当前生产图固定执行 | 引入外部实时资料；失败时降级为空 |
| Web | `WEB_SEARCH_TOP_K` | 5 | Web 候选数量 |
| RRF | `RRF_K` | 60 | 控制排名位置差异对融合分数的影响 |
| RRF | 普通 / HyDE 权重 | 1.0 / 0.8 | 两路本地检索的融合权重 |
| RRF | `RRF_TOP_K` | 12 | 进入 Rerank 的本地候选数量 |
| Rerank | `RERANK_MIN_TOPK` | 2 | 动态截断最少保留数量 |
| Rerank | `RERANK_MAX_TOPK` | 6 | 动态截断最多保留数量 |
| Rerank | 相对 / 绝对断崖阈值 | 0.2 / 0.2 | 相邻分数差达到阈值时提前截断 |
| Rerank | `RERANK_MAX_PER_DOCUMENT` | 2 | 非单文件严格查询时，每份文档最多入选数量 |
| Answer | `ANSWER_MAX_CONTEXT_CHARS` | 20,000 | 最终回答可消费的上下文字符上限 |

### 2.2 当前评估反映的问题

最近一次 16 条 dev 样本评估中：

- Ragas Context Precision 均值约为 `0.8281`；
- Ragas Context Recall 均值约为 `0.8573`；
- HyDE、RRF 层 ID Recall 均约为 `0.8125`；
- Rerank 层 ID Recall 降至约 `0.6042`；
- Rerank 层 ID Precision 约为 `0.2417`，高于上游，但召回损失明显。

这说明当前动态 Rerank 确实提升了候选纯度，但部分题目的核心 chunk 在最终截断时被丢弃。因此：

- 精确回答模式应更积极地截断并限制最终上下文；
- 全面检索模式不仅要扩大初始候选池，还必须提高 Rerank 最少/最多保留数量并降低提前截断概率；
- 不能只调 `SEARCH_TOP_K`，否则候选虽然召回了，仍可能在 Rerank 阶段丢失。

Ragas Context Recall 与基于 chunk ID 的 Recall 衡量对象不同，不能要求数值完全一致。模式调优时应同时观察两类指标。

## 3. 四种模式的推荐参数

以下数值是首轮实验起点，不应直接视为最终最优值。正式上线前应使用同一金标题库分别评估，并结合延迟和成本校准。

| 参数 | 均衡模式（当前） | 精确回答模式 | 全面检索模式 | 自定义安全范围 |
|---|---:|---:|---:|---:|
| ANN 单路候选数 | 20 | 12 | 40 | 10～50 |
| 普通/HyDE 各路 Top-K | 10 | 6 | 20 | 5～25，且不大于 ANN 候选数 |
| Dense / Sparse 权重 | 0.6 / 0.4 | 0.6 / 0.4 | 0.6 / 0.4 | 各 0～1，总和必须为 1 |
| HyDE | 开启 | 开启、降低影响 | 开启 | 开启/关闭 |
| 普通 / HyDE RRF 权重 | 1.0 / 0.8 | 1.0 / 0.4 | 1.0 / 1.0 | 0～1.5 |
| RRF K | 60 | 40 | 60 | 10～100，建议仅管理员可见 |
| RRF 输出数 | 12 | 8 | 24 | 5～30 |
| Rerank 最少保留 | 2 | 1 | 6 | 1～8 |
| Rerank 最多保留 | 6 | 3 | 12 | 最少保留值～12 |
| Rerank 相对断崖阈值 | 0.2 | 0.10 | 0.35 | 0.05～0.50 |
| Rerank 绝对断崖阈值 | 0.2 | 0.10 | 0.35 | 0.05～0.50 |
| 单文档最多上下文 | 2 | 2 | 3 | 1～5 |
| Web 检索 | 开启，保持当前行为 | 默认关闭 | 开启 | 开启/关闭 |
| Web Top-K | 5 | 3（开启时） | 8 | 1～10 |
| Answer 上下文字符上限 | 20,000 | 12,000 | 30,000 | 5,000～30,000 |

### 3.1 均衡模式

均衡模式必须精确保持当前生产参数和 Web 行为，不能在引入模式功能时顺便改变默认效果。它适用于用户没有明确偏好的一般问答，也是上线新功能时的回退模式。

### 3.2 精确回答模式

目标是减少弱相关材料进入答案生成阶段：

- 缩小普通检索、HyDE、RRF 候选池；
- 降低 HyDE 在 RRF 中的权重，减少假设性扩展带来的语义漂移；
- 降低 Rerank 断崖阈值，使系统更容易在明显分差处提前停止；
- 最终只保留 1～3 条高分上下文；
- 默认关闭 Web，避免外部结果干扰明确的内部资料问题；
- 鼓励用户使用文件、地域、文档类型等范围过滤。

适合：明确事实、单条规定、具体数值、指定文件内查询、操作条件查询。

风险：跨章节、多文档归纳题可能因上下文不足而漏答。前台应提示“材料更少、更聚焦，可能遗漏跨文档信息”。

### 3.3 全面检索模式

目标是尽量不漏掉支撑答案所需的材料：

- 扩大 ANN、普通检索、HyDE 和 RRF 候选数量；
- 保持或提高 HyDE 权重；
- 将 Rerank 最少保留提高至 6，最多保留提高至 12；
- 提高断崖阈值，使动态截断不容易过早发生；
- 提高同一文档最多上下文数量，允许连续章节共同支撑答案；
- 启用 Web 并扩大 Web 候选，但仍需经过统一 Rerank；
- 提高最终回答上下文预算。

适合：方案归纳、跨章节比较、多文档综合、原因与措施汇总、用户明确要求“尽量全面”的问题。

风险：延迟、Token 消耗和噪声上升，Context Precision 可能下降。前台应提示“覆盖更全面，但回答更慢、材料可能更多”。

### 3.4 自定义模式

不建议把所有底层常量原样暴露给普通用户。首版自定义界面建议只提供以下六项：

1. **候选搜索范围**：5～25，后台映射到 `SEARCH_TOP_K`，并自动设置合理的 ANN 候选数和 RRF 输出数。
2. **最终参考材料数**：1～12，映射到 Rerank 最少/最多保留数量。
3. **检索偏好**：“偏关键词—均衡—偏语义”，映射到 Dense/Sparse 权重。
4. **HyDE 语义扩展**：开关；高级用户可再选择低/中/高影响。
5. **联网检索**：开关，并明确提示资料来源和额外延迟。
6. **资料范围**：文件、地域、文档类型、主题和关键词筛选。

`RRF_K`、Rerank token 上限、HyDE 字符上限、摘要字符比例、连接超时等工程参数应保留在后台或管理员界面。这些参数难以被普通用户正确理解，而且错误设置容易导致性能问题。

## 4. 用户可使用的资料筛选条件

当前链路已经存在以下查询范围字段：

| 筛选项 | 当前处理方式 | 是否建议前台开放 | 说明 |
|---|---|---|---|
| 文件 `file_titles` | 可作为软条件；满足严格条件时可硬过滤 | 是 | 应使用文件选择器，不建议用户手输完整标题 |
| 地域 `region_names` | 可作为软条件或 Milvus 硬过滤 | 是 | 非严格模式会同时保留“全国”资料 |
| 文档类型 `document_types` | 支持政策、标准、规划、技术文件、其他 | 是 | 适合多选下拉框 |
| 主题 `topics` | 当前只加入检索文本，不做硬过滤 | 是 | 应明确标注为“检索偏好”而非严格筛选 |
| 关键词 `keywords` | 当前只加入检索文本，不做硬过滤 | 是 | 用于强化召回，不保证结果必须包含该词 |
| `strict` | 控制严格范围语义 | 有条件开放 | 建议显示为“仅搜索所选范围”，并给出漏检警告 |
| `hard_fields` | 指定真正进入 Milvus 过滤表达式的字段 | 不直接开放 | 后台根据用户勾选的严格范围生成 |

注意事项：

- 文件标题目前没有独立权威目录校验逻辑。若前台开放文件筛选，应由后台提供真实文件列表和稳定 ID，避免用户手输错误标题导致空结果。
- “主题”和“关键词”目前不是硬过滤条件，前台不能用“只看该主题”之类会造成误解的描述。
- 严格过滤通常提高 Precision，但选错范围会使 Recall 直接降为零。查询无结果时应允许用户一键“放宽范围重试”。

## 5. 推荐的前台交互

### 5.1 主界面

在输入框附近放置模式选择器：

- **均衡**：速度、准确和完整度平衡；
- **精确回答**：优先使用少量高度相关材料；
- **全面检索**：尽量覆盖更多章节和来源；
- **自定义**：自行调整检索范围和材料数量。

模式应是“每次请求”的属性，而不是全局服务器配置。可以额外提供“本会话记住选择”，但默认不要让上一次会话的自定义参数静默影响新会话。

### 5.2 自定义面板

建议使用业务语言而不是代码常量：

- 搜索范围：窄 / 中 / 广；
- 最终参考材料：1～12；
- 匹配偏好：关键词 / 均衡 / 语义；
- HyDE 语义扩展：关闭 / 开启；
- 联网搜索：关闭 / 开启；
- 资料范围：文件、地域、文档类型、主题、关键词。

界面应实时显示大致影响，例如：

> 预计保留 2～3 条材料；速度较快；适合明确事实查询。

或：

> 预计保留 6～12 条材料；覆盖更全面；响应时间和模型消耗会增加。

### 5.3 结果反馈

回答界面建议返回并展示：

- 实际应用的模式；
- 实际采用的资料范围；
- 本地候选数、Web 候选数和最终上下文数；
- 是否发生降级，例如 HyDE/Web/Reranker 失败；
- “用精确模式重试”和“用全面模式重试”的快捷操作。

不建议向普通用户直接展示 RRF 分数或所有底层参数。详细参数可放入调试信息或管理员审计页。

## 6. 后端设计原则（后续实现参考）

本阶段不修改代码。后续实现建议遵循以下结构：

1. 请求增加 `retrieval_mode`，取值限定为 `balanced`、`precision`、`recall`、`custom`。
2. 仅在 `custom` 时接受 `retrieval_options`；所有字段采用白名单、类型校验和上下限校验。
3. 请求入口将模式预设和自定义字段解析为一份完整的 `effective_retrieval_config`。
4. `effective_retrieval_config` 随 Query state 传递到 Embedding、HyDE、Web、RRF、Rerank 和 Answer 节点。
5. 节点读取请求级配置；缺失时回退当前常量，确保旧调用方与生产默认行为不变。
6. 禁止修改模块级配置常量来实现请求级模式，避免并发串值。
7. 响应、日志和会话历史记录模式名称及有效配置摘要，但不记录密钥或内部 Prompt。
8. SSE 与非流式入口必须使用同一套配置解析逻辑，防止两类查询效果不一致。
9. 对候选数量、上下文字符数、Web 调用和耗时设置服务端硬上限，前台传值不能绕过。

建议概念请求字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `retrieval_mode` | 枚举 | 四种模式之一，默认 `balanced` |
| `retrieval_options` | 对象或空 | 仅自定义模式使用 |
| `query_scope` | 对象或空 | 用户显式选择的文件、地域、类型、主题和关键词 |
| `remember_for_session` | 布尔 | 是否在当前会话沿用模式，默认 false |

## 7. 验证方案与上线门槛

每一种预设都应使用同一份金标题库独立评估，并保存模式和完整配置快照。除五项 Ragas 指标外，重点比较四层 ID 指标、延迟和最终上下文数量。

建议验收方向：

| 模式 | 首要目标 | 约束指标 |
|---|---|---|
| 均衡 | 与当前基线一致 | 五项指标和延迟不出现非预期回退 |
| 精确回答 | Context Precision、Rerank ID Precision 提升 | Context Recall 和 Must-hit Rate 的下降应在可接受范围内 |
| 全面检索 | Context Recall、Rerank ID Recall、Must-hit Rate 提升 | Context Precision、延迟和 Token 消耗不能无上限恶化 |
| 自定义 | 参数确实按请求生效 | 非法参数被拒绝，不影响其他并发请求 |

还应按题型分别统计：

- 单 chunk 直接事实题；
- 多 chunk 综合题；
- 多文档题；
- 指定文件/地域/文档类型题；
- 未来的不可回答题。

由于 Ragas 评审含模型随机性，正式比较建议每种模式至少重复 3 次并报告均值与波动；ID 指标是确定性诊断的主依据。不能只根据单次总体均值决定参数。

## 8. 推荐实施顺序

1. 先实现请求级配置模型、四个预设和配置快照，不改前台。
2. 用现有 dev 金标离线跑四种模式，校准推荐值。
3. 接入 API 和 SSE，并验证同一配置在两种入口下结果一致。
4. 前台先上线三种预设，观察真实使用分布和延迟。
5. 最后开放受限的自定义面板，不直接开放所有底层常量。
6. 积累真实查询后，可增加“系统推荐模式”，但仍让用户确认；首版不建议由模型静默替用户切换模式。

总体上，四模式设计值得实施。最关键的工程边界是：**用户选择的是受控的请求级检索策略，而不是直接修改服务器全局配置。**
