# query 模块修改设计

## 1. 文档目标与范围

本文基于现有 query 代码和新版 import 数据结构，提出 query 环节的调整方向，作为后续实现前的业务设计依据。

本次设计遵循以下边界：

- 保留现有 LangGraph 主流程及并行检索框架。
- 保留现有大模型、BGE-M3 稠密/稀疏向量、Milvus、RRF、BGE Reranker、DashScope MCP 网络搜索、MongoDB 会话历史和 SSE 输出能力。
- 不新增数据库、中间件或外部服务。
- 不编写实现代码，不展开具体函数步骤。
- 修改重点是统一 import 与 query 的字段契约、消除旧商品知识库语义、改善多路检索的容错和结果表达。

新版 import 写入的核心字段为：

```text
chunk_id、document_id、chunk_index、file_title、section_title、content、
context_type、region_names、document_type、topics、keywords、token_count、
dense_vector、sparse_vector
```

query 后续必须以这套字段为唯一的本地知识库契约，不再依赖：

```text
item_name、title、parent_title、part
```

---

## 2. 现有 query 流程概览

当前 LangGraph 主链路为：

```text
问题主体确认与问题改写
  -> 普通混合检索 ─┐
  -> HyDE 混合检索 ├-> RRF -> Reranker -> 答案生成 -> END
  -> 网络搜索 ──────┘
```

如果入口节点不能确认 `item_name`，则提前生成澄清文本并直接进入答案输出节点。

这个框架本身可以继续使用。普通检索擅长保持原问题语义，HyDE 擅长补充用户问题与文档表述之间的语义差异，网络搜索负责补充知识库外信息，RRF 和 Reranker 分别负责多路融合与精排，职责方向合理。主要问题集中在入口约束、字段契约、节点接口和失败处理方式。

---

## 3. 当前代码与新版 import 的主要断点

| 断点 | 当前 query 行为 | 新版 import 情况 | 影响 |
| --- | --- | --- | --- |
| 文档主体 | 强制识别并确认 `item_names` | 不再生成 `item_name` | 普通问题无法进入检索 |
| 名称集合 | 查询独立 `item_name_collection` | import 不再维护该集合 | 名称数据会缺失或逐渐过期 |
| Milvus 过滤 | 使用 `item_name in [...]` | chunks collection 无 `item_name` | 检索表达式直接失效 |
| 输出字段 | 读取 `title/parent_title/part/item_name` | 这些字段已移除 | 结果元数据为空或查询报错 |
| 展示标题 | 主要使用旧 `title` | 新约定为 `file_title + section_title` | 引用和展示无法对应新数据 |
| collection 名称 | query 固定读取配置名称 | import 遇到旧 schema 时可能写入版本化集合 | import 和 query 可能连接两个不同集合 |
| 并行分支容错 | 普通检索、HyDE、Web 任一为空都可能终止后续 | 空结果和外部搜索失败是正常退化场景 | 局部失败被放大为全链路失败 |
| 节点返回契约 | service 返回状态片段后，节点存在再次嵌套的情况 | 下游预期字段为列表 | 状态类型可能变成字典套字典 |
| 公共入口命名 | 部分节点和包导出的名称与 service 实际名称不一致 | 与 import 无关，但影响 query 启动 | 可能在导入模块或运行节点时失败 |
| HyDE 集合属性 | 与普通检索使用的 gateway 属性名不一致 | gateway 只提供统一 chunks collection 属性 | 两路检索可能不能访问同一集合 |

这些问题应先作为 query 改造的接口基线统一，否则只替换字段名仍不能形成稳定链路。

## 4. 整体修改思路

### 4.1 保留图结构，替换入口节点的业务含义

现有第一个节点不应再承担“必须确认文档名称”的职责，而应调整为“查询理解”。节点在图中的位置、条件路由能力和所用大模型均可保留，其输出语义改为：

- 根据当前问题和有限历史对话生成独立、完整的 `rewritten_query`。
- 识别用户明确提出的地域、文档类型、文件标题、主题或关键词限制。
- 区分硬过滤条件与软检索提示。
- 只有问题为空、指代确实无法消解或关键限制互相冲突时才要求用户澄清。
- 没有指定文件名称或地域时，允许直接执行全库检索，不能再提前终止。

这样可以保留现有“入口节点 -> 条件路由 -> 三路并行检索”的整体框架，同时使它符合面向政策、标准、规划和技术文件的知识库语义。

### 4.2 从“主体名称强约束”改为“语义召回 + 可选 metadata 约束”

检索主干应以改写问题的稠密、稀疏混合召回为基础。结构化 metadata 只在用户明确表达限制且字段值可靠时参与 Milvus 过滤。

推荐分为两层：

- 硬条件：用户明确指定的文件标题、地域或文档类型。这类条件可以进入 Milvus 标量过滤，但必须使用受控字段、枚举校验和安全转义。
- 软条件：模型推测的主题、关键词、可能地域或模糊文件名称。这类信息用于丰富改写问题或交给 Reranker 判断，不直接排除候选。

原则是“宁可多召回后精排，不因不确定 metadata 过早漏召回”。

### 4.3 建立 import 与 query 共用的结果契约

普通检索和 HyDE 检索都应输出同一种本地候选结构。建议候选结果包含：

| 字段 | 作用 |
| --- | --- |
| `chunk_id` | 本地 chunk 唯一标识，也是 RRF 去重主键 |
| `document_id` | 文档级聚合、限流和追踪标识 |
| `chunk_index` | 同一文档内的原始顺序 |
| `file_title` | 文件标题 |
| `section_title` | 章节标题 |
| `display_title` | 查询侧即时生成的展示标题 |
| `content` | 保留的完整原文，用于最终回答 |
| `context_type` | `text`、`table`、`code` |
| `region_names` | 主体地域 |
| `document_type` | 中文文档类型 |
| `topics` | 主题列表 |
| `keywords` | 关键词列表 |
| `score` | 当前阶段的检索或排序分数 |
| `source` | `milvus` 或 `web` |
| `url` | 网络来源地址；本地结果可为空 |

`display_title` 不需要写回 Milvus，统一按以下规则生成：

```text
section_title 非空且不同于 file_title：file_title / section_title
否则：file_title
```

网络结果在进入 Reranker 前映射到同一最小语义结构，使用网页标题作为 `display_title`、摘要作为 `content`、网页地址作为 `url`，本地专属 metadata 留空即可。

### 4.4 collection 必须只有一个有效来源

新版 import 会在配置集合仍是旧 schema 时选择版本化集合，例如从基础名称切换到 `_v2`。当前 query 直接读取基础配置名称，会产生“新数据写入新集合、查询仍访问旧集合”的风险。

后续必须让 import 和 query 共享同一个“当前生效 chunks collection”名称。推荐顺序为：

1. 部署或迁移时明确配置新版集合名称，import 和 query 均只读取该配置。
2. 如果需要无停机切换，可使用 Milvus alias 指向当前版本，但仍由一处配置表达有效入口。
3. 不建议 import 和 query 各自独立猜测版本号，因为两侧可能解析出不同结果。

这不需要新增资源，只需统一现有 Milvus 集合的配置和切换策略。

### 4.5 各检索分支允许独立退化

并行检索的价值在于互补，因此不应要求所有分支都必须返回结果：

- 普通检索为空时，允许使用 HyDE 和 Web 结果继续。
- HyDE 生成或检索失败时，允许普通检索和 Web 继续。
- Web 搜索超时或无结果时，允许仅根据本地知识库回答。
- RRF 至少接收一个非空本地召回列表即可工作；两路都为空时输出空本地候选，而不是在融合层制造异常。
- Reranker 的必要条件应是“存在至少一个本地或 Web 候选”，而不是“两类候选都非空”。
- 所有候选均为空时，答案节点输出明确的无检索结果提示。

这属于业务退化，不改变原有资源和节点拓扑。

## 5. 检索过滤原则

### 5.1 文件标题

`file_title` 适合用户明确指定某份文件时使用。对完全一致且已经确认的标题可作为硬过滤；对简称、错别字或不完整标题，应作为软条件加入查询文本，不能直接做等值过滤。

独立 `item_name_collection` 不再适合作为主链路依赖，因为新版 import 不维护它。可保留该集合本身以兼容旧数据，但不应阻断新版查询。

如后续确实需要文档标题自动补全，有两个决策方向：

| 方案 | 优点 | 问题 | 建议 |
| --- | --- | --- | --- |
| 主链路直接使用 chunks 中的 `file_title` | 与新版 import 一致，无额外同步 | 标题模糊匹配能力有限 | 当前推荐 |
| 将独立名称集合改造成文件标题目录 | 可做标题候选确认 | import 需要额外维护，产生双写一致性问题 | 有明确产品需求后再考虑 |

### 5.2 地域

`region_names` 表示文档主体适用或研究地域，不等同于正文中偶然出现的地名。地域过滤应遵循：

- 用户未指定地域时不加过滤。
- 用户明确指定地域时，可召回该地域文档，同时考虑适用范围为“全国”的文档。
- “不限”代表主体地域不明确或不受地域限制，不应简单等同于“全国”。是否纳入地域限定问题，应根据问题类型制定策略。
- 政策、标准、规划类问题更强调适用范围；技术文件和其他类问题更适合把地域作为软条件，避免漏掉通用技术材料。

建议在实现前明确以下产品规则：查询某城市时，是否同时包含“全国”和“不限”。推荐默认包含“全国”，将“不限”作为软召回候选，由 Reranker 判断相关性。

### 5.3 文档类型

`document_type` 只能使用 import 约定的中文枚举：

```text
政策、标准、规划、技术文件、其他
```

只有用户明确要求“查政策”“依据什么标准”等场景才使用硬过滤。普通事实性问题不应由模型自行猜测文档类型后限制召回。

### 5.4 主题与关键词

`topics` 和 `keywords` 主要服务于召回增强、解释和后续评测。由于它们来自 LLM 抽取，存在表达差异，不宜默认作为严格过滤项。

推荐用途：

- 加入改写问题，增强稀疏检索命中。
- 作为候选与问题是否同主题的辅助信息交给 Reranker。
- 在需要可解释性时展示“命中的主题/关键词”。
- 经过离线评测证明稳定后，再考虑特定场景下的数组过滤。

### 5.5 表格和代码块

`context_type` 不应改变基础召回算法，但需要保留到最终答案阶段：

- 表格内容应保持 import 生成的完整表头和行结构，避免在重排压缩时破坏字段对应关系。
- 代码块应保持围栏和必要上下文，不能在答案组装时当成普通段落随意拼接。
- 如果用户明确询问数值、对比、参数或计算规则，可在 Reranker 阶段适度提高 `table` 候选的关注度；这属于后续评测项，不建议一开始写死权重。

## 6. 各 service 的核心作用

### 6.1 `item_name_confirm_service.py`

建议保留文件和入口节点位置以降低改造范围，但将其业务定位调整为“查询理解与范围识别服务”。

核心作用：

- 校验会话和原始问题。
- 利用当前问题及有限历史完成指代消解和问题改写。
- 抽取可选的 `file_titles`、`region_names`、`document_types`、`topics`、`keywords` 查询范围。
- 标记哪些范围来自用户明确表达，哪些只是模型推测。
- 仅在问题确实无法理解时生成澄清回答。
- 记录本轮用户问题、改写问题和查询范围。

名称是否继续保留是兼容性决策。业务上更准确的名称应接近 `query_understanding_service.py`；如果暂时不改文件名，也应先替换其中的旧商品/主体语义。

### 6.2 `search_embedding_service.py`

核心作用：执行本地知识库的直接混合召回。

- 使用 `rewritten_query` 生成 BGE-M3 稠密和稀疏向量。
- 根据可信的硬条件构造可选 Milvus metadata 过滤。
- 从当前生效的新版 chunks collection 检索。
- 只读取新版 schema 字段，并映射为统一候选结构。
- 没有结构化过滤条件时执行全库语义检索，不再要求 `item_names`。

该分支是本地召回的稳定基线，应尽量少依赖 LLM 推测结果。

### 6.3 `search_embedding_hyde_service.py`

核心作用：通过假设性文档表达补充直接检索可能遗漏的语义结果。

- 使用改写问题和明确查询范围生成简短 HyDE 文本。
- 将问题与 HyDE 文本组合后生成向量并执行混合检索。
- 与普通检索使用完全相同的 collection、过滤条件、输出字段和候选结构。
- HyDE 文本只服务于召回，不作为最终事实依据，也不能直接进入答案上下文。

该分支应是增强分支而非必需分支，失败时不能阻断普通检索。

### 6.4 `web_search_service.py`

核心作用：使用现有 DashScope MCP 搜索补充外部信息。

- 使用独立完整的 `rewritten_query`，必要时带上用户明确的地域或文档类型描述。
- 将远端结果规范化为网页标题、摘要、URL 和来源类型。
- 对连接失败、超时、结构异常和空结果进行降级。
- 不把网页摘要当作本地知识库原文，也不伪造本地 metadata。

是否每次都联网可作为后续成本和时效性决策；在保持当前图结构的前提下，可先继续默认并行执行。

### 6.5 `rrf_service.py`

核心作用：融合普通检索和 HyDE 两路本地候选，消除两种召回分数尺度差异。

- 使用 `chunk_id` 作为本地候选去重键。
- 保留候选的全部新版 metadata，不因融合丢失标题、地域、类型等信息。
- 支持任一路为空时使用另一条结果继续。
- 输出统一、有序的本地候选集供 Reranker 使用。

网络结果目前在 Reranker 阶段与本地结果合并即可，RRF 无需强行将无稳定检索分数的网页结果纳入排名计算。若保持现有图边，Web 节点到 RRF 只承担并行汇合屏障，不改变 RRF 的本地融合职责。

### 6.6 `rerank_service.py`

核心作用：统一本地和网络候选，使用现有 BGE Reranker 精排并控制最终上下文数量。

- 将 RRF 本地结果和 Web 结果转换为统一候选结构。
- 使用 `rewritten_query + content` 计算相关性。
- 超长内容的精简文本只用于重排模型打分，最终答案仍使用未损坏的原始 `content`。
- 保留 `file_title`、`section_title`、`context_type`、地域、文档类型、来源和 URL。
- 支持仅本地、仅网络以及本地与网络同时存在三种输入。
- 动态 Top-K 需要处理空列表、零分、同分和候选不足等边界情况。

可增加同一文档或同一章节的候选数量上限，避免最终上下文全部来自一篇文档的相邻 chunks。是否启用应由检索评测决定。

### 6.7 `answer_output_service.py`

核心作用：基于精排后的证据生成最终回答，并完成流式输出、引用表达、图片提取和会话落库。

- 答案事实仍只能来自最终参考内容，历史对话只用于理解上下文。
- 删除 Prompt 中“`item_names` 是核心锚点”的强制规则，改为使用可选查询范围。
- 本地证据按 `file_title / section_title` 展示；网络证据显示网页标题和 URL。
- 清楚区分“本地知识库”和“网络搜索”来源。
- 当证据不足时明确说明，不使用 HyDE 假设文本或模型自身知识补全事实。
- 保留当前流式与非流式输出、图片 URL 提取和 MongoDB 历史记录能力。

## 7. 状态与节点契约建议

### 7.1 建议状态语义

保留现有主状态结构，并将辅助信息调整为：

| 状态 | 含义 |
| --- | --- |
| `original_query` | 用户原始问题 |
| `rewritten_query` | 可独立检索的问题 |
| `query_filters` | 结构化查询范围及其可信来源 |
| `embedding_chunks` | 普通本地召回列表 |
| `hyde_embedding_chunks` | HyDE 本地召回列表 |
| `web_search_docs` | 网络候选列表 |
| `rrf_chunks` | 两路本地召回融合结果 |
| `reranked_docs` | 本地与网络统一精排结果 |
| `answer` | 澄清文本、兜底文本或最终答案 |
| `image_urls` | 从最终证据中提取的图片地址 |

`query_filters` 建议表达“字段值、是否硬过滤、值的来源或置信状态”，避免仅使用若干字符串列表后无法判断是否应该过滤。

### 7.2 节点与 service 返回边界

后续实现必须选择并统一一种约定：

- service 返回具体业务值，节点负责包装成状态增量；或
- service 直接返回状态增量，节点原样返回。

不能同时包装两次，也不建议并行节点直接修改完整共享状态。每个并行节点只返回自己拥有的字段，可以减少 LangGraph 合并时的覆盖和类型错误。

节点层继续只负责：进度登记、调用 service、返回状态增量。参数校验、外部调用、结果映射和降级策略仍放在 service 层。

### 7.3 历史记录兼容

MongoDB 资源可以保持不变，但历史语义应从 `item_names` 迁移到查询范围：

- 新记录保存原始问题、改写问题、必要的查询范围和回答。
- 读取旧记录时允许继续识别 `item_names`，仅将其视为旧版文件标题线索。
- 新 Prompt 不应过滤掉所有没有 `item_names` 的历史消息。
- 历史内容只做指代消解，不能作为事实证据。

为了降低一次性改造风险，可以暂时保留 `item_names` 字段的读写兼容，但 query 主流程不能再依赖其非空。

---

## 8. Prompt 调整方向

### 8.1 查询理解 Prompt

由“提取政策/标准/规划文档名称”改为：

- 生成不超过合理长度的独立检索问题。
- 抽取用户明确表达的文件标题、地域、文档类型、主题和关键词。
- 不确定的值标记为软条件，不擅自生成硬过滤。
- 没有指定文档名称时正常返回改写问题。
- 使用与 import 一致的中文 `document_type` 枚举。

### 8.2 HyDE Prompt

继续生成领域内可能出现的简洁回答表述，但应强调：

- 只用于检索表达扩展。
- 不生成引用、来源或虚构文件名称。
- 用户明确地域或文档类型时保持该范围。

### 8.3 答案 Prompt

由 `item_names` 强锚定改为证据强锚定：

- 每个关键结论必须能对应参考内容。
- 本地证据优先显示 `file_title / section_title`。
- 网络证据与本地证据清楚区分。
- `score` 只表示排序相关性，不应在答案中解释为事实置信度。
- 表格、代码和普通文本按其结构引用，不改变原意。
- 参考内容不足时直接说明信息不足。

## 9. 容错、日志与可观测性

后续实现应围绕“单分支失败可退化、核心契约错误立即暴露”记录日志。

建议 INFO 日志：

- 本轮路由结果和是否需要澄清。
- 当前生效的 chunks collection 名称及 schema 版本。
- 实际启用的硬过滤字段，不记录完整用户隐私内容。
- 普通检索、HyDE、Web、RRF、Reranker 各阶段的输入输出数量。
- 最终本地与网络证据数量、文档数量和来源分布。

建议 WARNING 日志：

- 某一路召回为空或外部搜索超时，但仍可使用其他分支继续。
- LLM 输出了非法 document type、空数组或无法安全应用的过滤条件。
- 命中过多同文档相邻 chunks，可能影响证据多样性。
- 读取到旧版 `item_names` 历史记录或旧 schema collection。

建议 ERROR 日志：

- import 与 query 指向不同的有效 collection。
- Milvus 缺少新版必要字段或向量维度不一致。
- 节点返回字段类型不符合状态契约。
- 所有检索分支都失败且无法形成答案上下文。

日志不应输出完整 Prompt、完整文档正文、向量内容、API Key 或大量原始搜索结果。

## 10. 修改优先级

### P0：先保证链路和数据契约一致

- 统一节点调用名称、包导出名称和 service 实际入口名称。
- 统一节点与 service 的返回类型，消除重复包装。
- 统一普通检索与 HyDE 使用的 chunks collection 属性。
- 让 import 与 query 指向同一个新版 collection。
- 将所有本地检索过滤和输出字段迁移到新版 schema。
- 取消 `item_names` 非空才能检索的硬前置条件。

### P1：建立正确的查询业务逻辑

- 将入口服务改为查询理解与可选范围抽取。
- 为 metadata 建立硬条件和软条件策略。
- 统一本地与 Web 候选结构。
- 修改 RRF、Reranker 和答案 Prompt 的字段与展示规则。
- 支持任一检索分支为空时降级继续。

### P2：通过评测优化效果

- 调整普通检索与 HyDE 的召回数量和 RRF 权重。
- 评估地域中“全国/不限”的纳入策略。
- 评估同文档、同章节候选限流。
- 评估 `topics/keywords/context_type` 是否需要参与加权。
- 评估是否所有问题都需要默认网络搜索。

## 11. 建议的验收场景

后续实现完成后，至少覆盖以下业务场景：

1. 未指定文件名称的普通问题可以直接全库检索。
2. 明确指定文件标题时，结果集中在对应文件。
3. 指定北京市政策时，能正确处理“北京市”和“全国”的适用范围。
4. 查询技术参数时能召回并完整保留表格内容。
5. 普通检索为空但 HyDE 有结果时仍可回答。
6. HyDE 失败时普通检索仍可回答。
7. Web 搜索失败或为空时本地知识库仍可回答。
8. 本地为空但 Web 有结果时能明确按网络来源回答。
9. 所有候选为空时输出稳定、明确的无结果提示。
10. 引用标题统一展示为 `file_title / section_title`。
11. 旧会话中的 `item_names` 不会导致新版查询异常。
12. import 写入的实际 collection 与 query 查询的 collection 完全一致。

## 12. 推荐的最终业务链路

```text
原始问题 + 有限历史
  -> 查询理解：问题改写 + 可选查询范围 + 是否需要澄清
  -> 若确需澄清：直接输出并记录历史
  -> 否则并行执行：
       1. 新版 chunks collection 直接混合检索
       2. HyDE 增强混合检索
       3. DashScope MCP 网络搜索
  -> RRF 融合两路本地候选
  -> Reranker 统一精排本地与网络候选
  -> 按 file_title / section_title 组织证据
  -> 基于证据生成答案、流式输出、提取图片并记录历史
```

最终改造的核心不是替换某几个字段，而是把 query 从“先确认某个商品或文件主体，再在主体内检索”调整为“先理解问题，以全库语义召回为基础，按用户明确范围进行可选过滤，再通过融合和精排收敛证据”。这样能够与新版 import 的通用文档模型保持一致，同时最大限度复用现有查询框架和基础资源。
