# 再生水行业 RAG 设计

## 1. 设计目标

本设计面向未来的再生水行业知识库，不沿用“先识别商品，再按商品过滤”的业务模型。目标是让系统能够按地域、文种、专业主题、时效和证据层级准确检索，并生成可追溯回答。

设计优先级依次为：Query Understanding、结构感知知识入库、Dense/Sparse Hybrid Retrieval、融合与 Rerank、带引用回答和可量化评估。完整版本管理、审核发布、权限和多租户不属于本阶段 RAG 核心设计。

## 2. 文档分类

### 2.1 一级文种

| 类型 | 示例范围 | 检索关注点 |
|---|---|---|
| 法规政策 | 法律、法规、规章、办法、通知、指导意见 | 发布机构、适用地域、效力、时效 |
| 标准规范 | 国标、行标、地标、团标、设计/运行规范 | 标准号、版本、强制性、替代关系、条款 |
| 规划文件 | 专项规划、总体规划、实施方案 | 规划期、地域、目标、指标和项目安排 |
| 科研论文 | 期刊、会议、学位论文 | 研究对象、方法、数据、结论、局限性 |
| 技术研究报告 | 咨询报告、专题研究、评估报告 | 委托方、研究范围、结论和适用边界 |

可以增加“企业内部制度、工程案例、设备资料”等类型，但是否纳入正式范围待确认。

### 2.2 地域层级

建议使用层级化行政区划字段，而不是单个自由文本：

```text
country: 中国
province: 广东省
city: 深圳市
district: 南山区
region_codes: [CN, CN-44, CN-4403, CN-440305]
region_level: district
```

全国性文件使用 `region_level=country`。跨地区研究可以使用多个 `applicable_regions`。行政区划编码标准待确认。

### 2.3 专业主题

建议建立受控词表，初始主题包括：

- 再生水水质与用途分类；
- 污水处理与再生工艺；
- 消毒、深度处理和膜技术；
- 工程规划与设计；
- 管网、泵站和调蓄设施；
- 运行维护与安全；
- 监测、检测与质量控制；
- 管理制度与监管要求；
- 价格、经营和激励政策；
- 节水、非常规水资源配置；
- 环境影响、风险和公众健康；
- 碳排放、能耗与资源化。

主题允许多标签。模型负责初步抽取，首阶段通过样本评测和离线检查保证质量；人工审核发布流程属于未来规划。

## 3. Metadata 设计

### 3.1 文档级 metadata

| 字段 | 类型 | 说明 |

| `document_type` | enum | 法规、标准、规划、论文、报告等 |
| `document_subtype` | string | 通知、地标、期刊论文等细分类型 |
| `document_number` | string | 文号或标准号 |
| `issuing_authority` | list[string] | 发布/编制机构 |
| `authors` | list[string] | 作者；政策文件可为空 |
| `source_url` | string | 官方或授权来源 |
| `source_name` | string | 来源网站/资料库 |
| `publish_date` | date | 发布日期 |
| `effective_date` | date | 生效日期 |
| `expiry_date` | date/null | 失效日期 |
| `validity_status` | enum | 现行、废止、失效、被替代、未知 |
| `replaces` / `replaced_by` | list[string] | 替代关系 |
| `region_codes` | list[string] | 适用或研究地域 |
| `region_level` | enum | 国家、省、市、区、跨区域等 |
| `topics` | list[string] | 专业主题标签 |

| `content_hash` | string | 去重和变更检测 |
| `parser_version` | string | 解析器和配置版本 |
| `ingested_at` | datetime | 入库时间 |

### 3.2 Chunk 级 metadata

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | string/int | chunk 唯一标识 |
| `document_id` | string | 追溯所属文档 |
| `section_path` | list[string] | 完整标题层级路径 |
| `section_title` | string | 当前章节或条款标题 |
| `clause_number` | string/null | 法规/标准条款号 |
| `page_start` / `page_end` | int/null | 原文页码 |
| `chunk_index` | int | 文档内顺序 |
| `content_type` | enum | 正文、表格、图片说明、公式、附录等 |
| `content` | string | 用于展示和回答的原始内容 |
| `embedding_text` | string | 用于向量化的规范化文本 |
| `token_count` | int | 实际 tokenizer 计数 |
| `region_codes` | list[string] | 继承并允许章节级覆盖 |
| `topics` | list[string] | 继承并允许章节级补充 |
| `validity_status` | enum | 冗余关键过滤字段 |
| `citation_label` | string | 可直接用于答案引用的定位文本 |

核心 metadata 抽取建议保存置信度和抽取方式（规则或模型），具体字段形态待确认。

这里的 `document_number`、发布日期、效力状态和替代关系是行业检索事实，不代表实现完整的文档版本管理系统。

## 4. 文档处理与 Chunk 策略

### 4.1 通用原则

- 先恢复文档结构，再按语义单位切分。
- 使用 token 数而非单纯字符数控制模型输入。
- 每个 chunk 必须能够定位到原文文档、章节和页码。
- 表格、图片说明、公式和脚注不能无条件混入相邻正文。
- 标题层级作为 metadata 保存，并适量加入 `embedding_text`。

### 4.2 分文种策略

法规政策：

- 优先按章、节、条、款、项切分。
- 单条较短时可合并相邻条，但不得跨越章节或责任主体边界。
- 保存条款号和适用条件。

标准规范：

- 按章节和条款号切分。
- 规范性要求、公式、参数表和注释尽量保持完整。
- 表格单独形成 chunk，并补充表名、列名及所在条款上下文。

规划文件和研究报告：

- 按标题层级和主题段落切分。
- 指标、目标、项目清单和时间节点应形成可独立检索单元。

科研论文：

- 按摘要、方法、结果、讨论、结论切分。
- 避免把研究条件与结论拆开；保存图表引用和实验对象。

### 4.3 初始参数建议

- 目标 chunk：约 400～800 tokens；
- 最大 chunk：约 1000 tokens；
- overlap：约 50～100 tokens，仅用于连续叙述段落；
- 法规/标准完整条款优先级高于固定长度参数。

以上是初始实验值，必须通过行业评测集调整，不能作为永久硬编码。

## 5. Embedding 设计

- 第一阶段可复用当前 BGE-M3 dense+sparse 能力。
- `embedding_text` 建议包含文档标题、章节路径、地域、文种、主题和正文，但不要堆叠无关 metadata。
- 查询和文档必须使用同一模型版本、归一化规则和 tokenizer 配置。
- 模型名称、向量维度、metric 和生成时间应可追踪。
- Embedding 批次失败必须重试或使该文档导入失败，不能静默丢失 chunk。
- 模型是否需要针对再生水语料微调，待基线评测后决定。

## 6. Milvus 索引与检索

### 6.1 建议集合

初期使用一个文档 chunk 集合即可完成核心 RAG 闭环，不把独立文档主数据库作为前置条件。

Chunk 集合包含：

- 主键和文档关联字段；
- Dense 向量；
- Sparse 向量；
- 高频过滤 metadata；
- 展示和引用需要的正文及定位字段。

### 6.2 检索流程

1. Query Rewrite 输出独立问题和结构化过滤意图。
2. 根据确定性过滤条件限定地域、文种、主题和有效性。
3. 分别执行 Dense、Sparse 检索。
4. 必要时增加标题、标准号、文号等精确检索。
5. 对多路结果执行 RRF/加权融合、去重和文档多样性控制。
6. Rerank 后生成证据集。

检索必须允许降级：某一路为空或联网搜索失败时，不应阻断其余知识库检索。

### 6.3 地域策略

- 用户明确深圳某区时，优先该区，其次深圳市、广东省、国家层级文件。
- 上级文件不能简单因地域更宽而降为无关，需要结合适用效力排序。
- 用户未指定地域时，可结合问题和会话推断，但不确定时应澄清。
- 其他省市资料应正常可检索，不能因深圳资料更多造成绝对排斥。

## 7. Query Rewrite

Query Rewrite 不再输出商品名称，应输出结构化检索计划，例如：

```json
{
  "standalone_query": "深圳市再生水用于城市杂用时适用哪些现行水质标准？",
  "regions": ["CN-4403"],
  "document_types": ["standard", "policy"],
  "topics": ["再生水水质", "城市杂用"],
  "time_scope": null,
  "validity": ["current", "unknown"],
  "comparison_mode": false,
  "clarification_needed": false,
  "clarification_question": null
}
```

要求：

- 结合会话历史补全指代，但不得擅自添加用户未表达的关键条件。
- 区分“适用要求”“技术研究结论”“规划目标”等不同意图。
- 识别地域冲突、时间范围、标准号和文号。
- 输出必须通过结构化模型校验，失败时退回原问题和宽松检索。

## 8. Rerank 与证据组织

- 第一阶段可复用现有 BGE Reranker，使用行业样本校准。
- Rerank 输入应包含问题、正文和必要标题路径。
- 对法规、标准类证据，可加入文种、效力和地域的业务加权，但必须与语义相关性分数分开记录。
- 避免最终证据全部来自同一文档的相邻 chunk；需要进行去重和多样性控制。
- 最终证据应保留 `document_id`、标题、章节、页码、来源和有效状态。
- 不同文件冲突时，不应由模型静默选择，需要向用户说明冲突和适用边界。

## 9. 回答与引用

- 答案必须基于检索证据，不足时明确说证据不足。
- 法规、标准类回答优先引用官方来源和现行版本。
- 每项关键结论附文档标题、条款/章节、页码或来源链接。
- 将“文件明确规定”“论文研究发现”“模型归纳建议”分开表述。
- 不把联网搜索摘要直接当作正式依据；必要时抓取并验证原文，具体机制待确认。

## 10. 评估方案

至少覆盖：

- 地域识别准确率；
- 文种和专业主题识别准确率；
- Chunk Recall@K、MRR、nDCG；
- 必须命中条款/标准命中率；
- Rerank 前后质量提升；
- 引用正确率和引用完整率；
- 答案忠实度、拒答合理性；
- 延迟、模型调用次数和成本。

评测集需要覆盖国家、广东、深圳和区级材料，以及水质、工艺、设计、运维、管理和经营等主题。正式数据与验收阈值待确认。

## 11. 未来规划（非核心 RAG）

- 完整的文档版本管理和变更发布；
- 人工审核工作台；
- 文档级权限和多租户过滤；
- 长期用户 Memory 对检索计划的个性化影响。

这些能力不应提前进入当前 Milvus Schema、Query Rewrite 或 Agent 主流程，除非出现明确业务需求。
